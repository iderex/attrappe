# 0003. A virtual clock, and the two places wall time is allowed

## Context

Every impairment in this emulator is a function of time. Warm-up is a function of
time since power-on. Drift is a function of time and temperature. The delay a
read costs is a function of the configured integration time. A timeout is a race
between the emulator's delay and the client's patience.

The numbers are not small. A warm-up specification runs to twenty or thirty
minutes. An integration time of ten power-line cycles costs two hundred
milliseconds a reading, and a test that reads a thousand times would spend three
minutes doing nothing.

None of that can be tested against a wall clock, and a project that pretends
otherwise ends up with either a slow suite or no test of its most characteristic
behaviour.

## Options considered

Wall clock everywhere, with tests that sleep.

Wall clock with a global speed multiplier applied to every configured delay.

An injected clock object that the tests control.

## Decision

Time is an injected dependency. A single clock interface provides the current
instrument time, a sleep, and the time elapsed since power-on. Two
implementations exist: a real clock that reads the system monotonic clock and
sleeps, and a manual clock whose time moves only when a test advances it.

Nothing in the emulator calls a time function directly. Every use goes through
the injected clock.

The manual clock is the default in the unit suite. The real clock is used in two
places and no others: the socket-level tests, where the delays are the emulator's
own configured ones, and the integration harness that drives real drivers.

## Reasons

An injected clock is the only option that makes warm-up and drift testable at
all. With a manual clock a test advances twenty minutes in a microsecond and
asserts what the reading did. With a wall clock that test cannot exist, so the
behaviour ships untested and the emulator's most distinctive property becomes the
one nobody checked.

A global speed multiplier looks cheaper and is not. It leaves real sleeps in the
code, so the suite is still slow in proportion, and it turns every timing
assertion into a tolerance question. It also cannot express what tests actually
want, which is to jump to a specific instant and inspect state there.

Forbidding direct time calls is what makes the injection real. One forgotten
direct call and a test that believes it advanced twenty minutes is reading a
value computed from the wall clock, and it will pass for the wrong reason.

The socket-level tests keep a real clock deliberately. A timeout is a race
between two parties, and a race with one side frozen is not the thing being
tested.

## Costs accepted

Every constructor in the emulator takes a clock, which is visible ceremony in
code that would otherwise be shorter.

The rule against direct time calls is a rule, and until a check refuses it, it is
a habit. The scaffolding milestone owes a lint rule that names the module and
refuses the import, with a test showing it bites on a one-line violation. Until
that rule exists this section is a statement in a document and nothing more.

## Consequences

The signal pipeline, the fault schedule and the session each take a clock.

The fault schedule is keyed to instrument time rather than to wall time, which is
what makes a scheduled fault reproducible and what lets a warm-up-related fault
be tested at all.

## Status

Accepted.
