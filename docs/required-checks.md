# Required checks

Generated by `python tools/required_checks.py` from the workflow files this tree
tracks. Do not edit it. `python tools/gate.py --only required-checks` refuses a
document that no longer matches the workflows, so a job renamed without
regenerating this turns the gate red.

**Nothing here has been applied.** No branch protection rule and no ruleset was
created or changed by the plan that produced this document. Requiring a check is a
repository setting and setting it is the maintainer's action. This exists so that
doing it is one sitting rather than an archaeology exercise.

A required check matches the check-run name literally. A job renamed later stops
being the check that was required, and the setting does not complain: it waits for a
check that will never arrive, or it silently gates on nothing, depending on how the
rule was written. That failure is quiet and it has bitten this class of setup before,
which is why the strings below are exact and why the check above exists.

A check run carries the job's `name` where the job has one and the job's key
otherwise. The workflow's name is shown beside it in the pull-request interface and
reads like a prefix, and is not one.

`Audit workflows (zizmor)`: yes for a pull request from this repository. Its job asks for a write permission so that it can upload findings, a fork's pull request is not granted one, and the upload step fails there. Requiring it would make every fork's pull request red for a reason that is not about the change.

`Gate / build / distribution`: yes. The name carries two slashes because a job that calls a reusable workflow produces one check run per job in the workflow it calls, named after both. The release path calls the same workflow, so requiring this requires the job a release is built by.

`Gate / dependencies`: yes, and it is the one whose red run can arrive without a commit. Its workflow also runs on a timer, so the mainline turns red when an advisory is published against a dependency nobody touched.

## Not candidates

These publish a result rather than refusing a change. Requiring one makes the merge
depend on a service outside this tree.

| Check-run name | Produced by | What it does | Why it is not a candidate |
| --- | --- | --- | --- |
| `Scorecard analysis` | `.github/workflows/scorecard.yml`, job `analysis` | nothing. It scores the repository and uploads the result | no. It publishes rather than refuses, it does not run on a pull request at all, and its score moves with a service outside this tree |
| `zizmor` | no job in this tree | the code-scanning check the workflow audit's upload creates. It publishes findings rather than refusing a change, and it is produced by a service rather than by a job here, so requiring it would make the gate depend on that service | the same reason |
| `update-pip-graph` | no job in this tree | the dependency-graph submission. Its run reports a workflow path of `dynamic/dependabot/update-graph`, which is generated by the service and is in no tree, and it appears only on a commit that moved the dependency set. It records rather than refuses, and a required check that only sometimes runs cannot be satisfied by a change that did not produce it | the same reason |

The last rows are not derived from the workflow files, because nothing in them
names those checks. They were observed instead, and the observation is repeatable:

```
gh api repos/iderex/attrappe/commits/ab980631426e35029e3d6967bac50a76908fd9ef/check-runs \
  --jq '[.check_runs[].name] | sort | .[]'
gh api repos/iderex/attrappe/commits/b59c7be47b87352d5a3df6a2e1164f8713739db8/check-runs \
  --jq '[.check_runs[].name] | sort | .[]'
gh api repos/iderex/attrappe/commits/be923136e248efe666f65701f20647e1ec9cbc4c/check-runs \
  --jq '[.check_runs[].name] | sort | .[]'
```

Two of those are mainline commits and one is a pull-request head, and the sets
differ in every direction: the pull-request-only guards appear on the head, the
push-only scorecard on the mainline ones, and the dependency-graph submission only
on the mainline commit that moved the dependency set. Compare against the table
above before requiring anything, because a check that does not run on a given
event cannot be satisfied by a change that raised it.

## What this list does not settle

It says which checks could be required. It does not say which should be, and it does
not say what happens to a pull request from a fork under a rule that requires a check
a fork's pull request cannot produce.
